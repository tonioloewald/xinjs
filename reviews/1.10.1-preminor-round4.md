## Blockers (fix before tag)

### B1 — The release notes document none of this diff's DOM behaviour changes, and one line in them is now false
`CHANGELOG.md` §[1.10.1] (lines 9–167). Verified by execution against **v1.10.0** (the version a consumer actually upgrades from), not just the review base.

`awk` over the 1.10.1 section: zero mentions of `fragment`, `hydrate`, or the component `content` array. The section spends a full paragraph justifying `div(false)` and surveying tosijs-ui for occurrences; these larger shape changes got nothing. Undisclosed, all measured:

| Call | v1.10.0 | HEAD |
|---|---|---|
| `fragment('a', null, 'b')` | `"anullb"` | `"ab"` |
| `fragment({class:'x'})`, `fragment([span('a')])`, `fragment(span)` | stringified junk | warn + drop |
| `fragment(app.name)` | bare Text node | `<span class="-tosi-data">` (live) |
| `content = [span('x:'), app.user.name]` | `<span>x:</span>Alice` — `[SPAN, #text]` | `<span>x:</span><span class="-tosi-data">Alice</span>` — `[SPAN, SPAN]`, live |
| `content = [10n, span(' each')]` | `<span> each</span>` (bigint dropped) | `10<span> each</span>` |
| same content array **in shadow DOM** | `<span>x:</span>Alice` (stale but visible) | `<span>x:</span><span class="-tosi-data"></span>` — **permanently empty**, plus a per-class warning |

Two consequences worth calling out by name in the notes: an **Element now sits where a text node did**, so consumer CSS keyed on `:last-child` / `> *` / `:nth-child` or code indexing `childNodes` silently changes meaning on a patch upgrade; and the shadow-DOM case **removes rendered text from the page** (bindings are inert in shadow DOM by design, so the new bound span never gets its initial `toDOM`).

The existing "A bare proxy is a live element child" bullet says **"Runtime unchanged"** — true for `div()`, false for `fragment()` and for `Component.hydrate()`. That sentence must be corrected, not merely supplemented.

Same edit, same document: **the size figures are 40–55 % low.** Measured with the build's own compressor, v1.10.0 → HEAD: `module.js` +427, `main.js` +429, `index.js` +411, `core.js` +410, `state.js` +443, `module.debug.js` +712, `module.safe.js` +731 (Bun-zlib: +452/+441/+403/+423/+453/+724/+734 — the understatement holds under either compressor). `CHANGELOG.md:13` says "+~290 gz per bundle"; `bin/bundles.ts:93` says "+264 gz". Neither was ever wrong when written — the "+264" was accurate at `b04caf9`; the "+~290" was already stale when written at `2dd0169` and survived two header re-scopes unmeasured. `Migration.md` is untouched (`git diff --stat v1.10.0..HEAD`), and `src/component.ts:141–143` still documents proxied content items as "pass through as children", i.e. the old behaviour.

**Fix:** add `### Changed` bullets naming (a) `content` arrays render text-valued items in argument position; (b) a proxy in a `content` array is a live child — the extra bound `<span>`, called out as the one shape that can change existing layout, **and** the shadow-DOM blanking; (c) `elements.fragment()` / `svgElements.fragment()` / `mathML.fragment()` now honour the positional contract. Restate both size figures from measurement. Correct the "Runtime unchanged" claim. Fix the stale doc block at `src/component.ts:141–143`.

*(Deduped: correctness-lens "CHANGELOG records none of this diff's behaviour changes", blast-radius "Three consumer-visible DOM behaviour changes ship with no CHANGELOG line", correctness "shadow-DOM content renders nothing", and efficiency "size numbers understate by ~50%" are one edit to one file.)*

### B2 — The test written to lock the fix in does not cover the site the fix changed
`src/elements.test.ts:734`. **Mutation-verified in a throwaway clone** (working tree never touched): re-adding the pre-fix hydrate branch (`if (classifyPositional(item) === 'proxy') { ordered.push(item); continue }`) at `src/component.ts:2731` leaves **987 pass, 0 fail** while fully restoring the round-3 M2 major (`content = [span('x:'), proxy]` back to a dead one-time string). The suite is blind to the entire remediation.

The block's own comment claims "these tests are what notices if a fourth site appears". The tests assert only `elements.div(proxy)` and `elements.div(elements.fragment(proxy))`. The hydrate parity block at `src/component.test.ts:2553–2626` covers value / nested-array / Text-node only. No test anywhere in `src/` puts a boxed proxy in a Component `content` array.

**Fix:** add the hydrate case — a component whose `content` array contains a boxed proxy, asserting the bound `<span class="-tosi-data">` appears *at its argument position* and that its text changes after `await updates()`. Add the shadow-DOM variant (assert the empty bound span **and** the warning), so B1's disclosure is pinned by a test. One line for `template(proxy)` placement while you are there.

*(Note: `template(proxy)`'s claimed before/after does not reproduce under happy-dom — happy-dom's `HTMLTemplateElement.append()` already routes into `.content` on both trees. The change is real in a browser and is an improvement; it is untested either way.)*

### B3 — `Component.content`'s TYPE was never widened alongside its runtime, and the docs added this release promise the widened form
`src/xin-types.ts:423–424` still reads `ContentType = ContentPart | ContentPart[]`, `ContentPart = Element | DocumentFragment | string`, while `f2d38c6` routes `hydrate()`'s content array through the same `applyPositional` as `div()`. Verified by `tsc`:

```
error TS2416: Property 'content' in type 'Probe' is not assignable to the same
property in base type 'Component<PartsMap>'.
  Type '(HTMLSpanElement | BoxedScalar<string>)[]' is not assignable to type 'ContentPart[]'
```

…while the identical `div(span('x:'), s.n)` typechecks, because `ElementPart` *was* widened. `src/component.ts:141–143` documents content-array items as applying "just as they would be applied to the element being created by `div()`". The release therefore ships a documented API that TypeScript rejects — the exact create/hydrate divergence this release exists to end, one layer up. The type half sits in the unreviewed `v1.10.0→3a242c1` range and the runtime half in this diff, so no pass has seen both.

**Fix:** widen `ContentType` to reuse `ElementPart` (or a shared alias), and add the case to `src/type-surface.test.ts`. If deferred instead, the doc block and CHANGELOG must say the array form is runtime-only pending a type widening — a shipped doc that lies is the same class of defect as B1.

### B4 — The mandatory browser lane has not been run on the final tree
CLAUDE.md makes `bun run test:browser` a non-`bun run build` gate for any release touching DOM behaviour. `f2d38c6` rewrites the child-placement path in **all three** of `create()`, `Component.hydrate()` and `fragment()`. The only evidence on this tree is happy-dom — and CLAUDE.md's own caveat is that happy-dom's zero geometry and cheap `tagName` produce silently-passing assertions and misleading perf framings in exactly this area. Round 3 said in as many words: "do not quote the happy-dom framing."

**Fix:** run `bun run test:browser` (Chromium + Firefox) on the final tree before tagging. Then re-run `bun run build` before committing — see the checklist follow-up below.

### B5 — `module.debug.js` has 36 gz bytes of headroom, in a file that twice forbids hair-trigger budgets
Measured under Bun (the compressor the gate runs): `module.debug.js` **59 464 / 59 500 → 36 B**, `module.safe.js` 59 323 / 59 500 → 177 B. `bin/bundles.ts`'s own comments call the budgets "a DECISION, not a measurement: ~1 kB of headroom", record that a 1.8.1 pass "by SEVEN bytes" is "the mistake not being repeated", and instruct that budgets be raised **deliberately, in the commit that caused the growth** — which is this release (+712/+731 on the pair).

The next ~40 bytes anywhere in the library fails `bun run build` mid-release, at exactly the moment the reflex is to raise the number rather than read it. *(Correction to the filed nit: `bun start` is safe — the tjs pair is excluded from `BUILT` on a non-`full` run, so only `bun run build` trips. The other three tight bundles are below policy but not hair-trigger; they are a follow-up, not a blocker.)*

**Fix:** re-baseline `module.debug.js` / `module.safe.js` to ~60 500 in the release commit, with the growth accounted for in the comment — or record per-bundle why a tighter ceiling is wanted for the experimental pair.
