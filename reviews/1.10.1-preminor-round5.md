## Blockers (fix before tag)

### B1 — The `ContentPart` widening is narrower than the doc table shipped in the same commit; 3 of 6 rows are still TS2416
`src/xin-types.ts:431` · lens correctness · **verified/confirmed**

Round 4's B3 asked to widen `ContentType` "to reuse `ElementPart` (or a shared alias)". A hand-written partial union was used instead, whose only object arm is `TosiProps<any>` — an interface with ~24 **required** members. `ElementPart` (`src/xin-types.ts:386`) carries `ElementProps<T> | Map<string, any>`, and `ElementProps` has `[key: string]: any`, which is exactly what absorbs the missing shapes. Reproduced with the same tsc invocation `type-surface.test.ts` uses, against `dist/index.d.ts`:

```
content = [elements.span('x'), new Date()]       -> TS2416 (Date not assignable to ContentPart)
content = [{ class: 'from-content' }, span('x')] -> TS2416
content = [new Map([['class','x']]), span('x')]  -> TS2416
```

All three **run correctly** (probed: Date renders in place; object and Map apply to the host), and the identical `div(...)` spellings typecheck clean. The doc table added in this same commit (`src/component.ts:145-152`) promises all three and states "the same code, so the two cannot drift." Neither branch of B3 was satisfied: `ContentPart`/`ContentType` appear nowhere in `CHANGELOG.md` and there is no runtime-only caveat.

Worse than filed: the verbatim `MyButton` doc example at `src/component.ts:131-137` (pre-existing) is also TS2416 in the function form once the param is typed. The new table extended an already-broken promise.

The gate written to catch this is blind: `src/type-surface.test.ts:213-221` probes `[span('x'), proxy, 10n, false, null]` — precisely the shapes the partial union already admits.

**Fix:** widen `ContentPart` to what the table documents (reuse `ElementPart` / a shared alias, as B3 asked). Extend the `Probe` class in `src/type-surface.test.ts` to compile a `Date`, a plain props object and a `Map`, so every table row is covered. If deferred, delete those rows from the table **and** say so in `CHANGELOG.md`.

*Re-review scope: correctness over the remediation diff only (type change + probe); re-run the tsc probes. No behavioural surface touched.*

### B2 — The new `hydrate()` single-content normalisation has no runtime test; deleting it leaves the suite fully green
`src/component.ts:2738-2750` · lens correctness (a coverage defect) · **verified/confirmed via mutation**

The eight-line normalisation is real and behaviour-changing: with it deleted, `content = someProxy` and `content = 10n` both throw `expect text content or document node` from `appendContentToElement` (`src/dom.ts:272`). Restoring it makes both pass. So the CHANGELOG claim is accurate — and the path is exercised by nothing.

Mutation-verified in a throwaway copy (repo never touched): baseline and mutated tree produce a byte-identical pass/fail list. Zero tests distinguish fixed from unfixed code. Grepping every `content =` assignment across `src/`, `tests/` and the doc fences: every runtime test assigns an array, a function, `null`, or a single `Element`. **The two tests added in this very commit** (`src/component.test.ts:2631-2698`) both use content **arrays** — the pre-existing branch, not the new one. The only reference to the single form is `ProbeSingle` (`src/type-surface.test.ts:220`), a tsc-compile probe that never instantiates the class and is additionally `test.skipIf(!existsSync('dist/index.d.ts'))`.

This is B2's failure class repeated one commit later, in the commit whose own `TODO.md` entry says "A fix can land with no test that exercises the site it changed, and nothing notices."

**Fix:** add runtime cases beside the new array tests in `src/component.test.ts` — `content = proxy` (assert a bound `<span class="-tosi-data">` with live text after `await updates()`), `content = 10n` (assert `"10"`), `content = { class: 'x' }` (assert the class lands on the host, no child appended). All three probed working; a ~15-line probe passes against HEAD as written.

## Major (fix now or file with a named owner)

### M1 — The new minimum-headroom gate never measures a real artifact in the `bun run build` lane
`src/entries.test.ts:331-352` · lens correctness · **verified/confirmed, with the mechanism worse than filed**

Build order verified: `bin/site.ts:798` calls `buildSite()`, whose prebuild does an unconditional `rm -rf dist`; `buildLibrary()` runs afterwards (`:806`) and its first act is `bun test src/` (`:239`), before any `Bun.build`. `restoreCommittedDist()` runs only on the dev path and in the watcher, so it does not repopulate during `bun run build`. The in-build loop (`bin/site.ts:445-465`) checks `bytes > budget` **only**; grep confirms `MIN_HEADROOM` exists nowhere else (`release-doctor.ts` has no size gate).

**Mechanism correction — it is not a skip, it is a vacuous pass.** `tosijs-site.config.ts:66` sets `libraryTsconfig: './tsconfig.build.json'`, which the orchestrator runs as `bun tsc -p` inside `buildSite`; that config emits `dist/module.js` (25 bytes — `src/module.ts` is `export * from './index'`). So `existsSync('dist/module.js')` is **true** at test time. Reproduced in a scratch cwd holding only those tsc stubs: skips 3→1, passes 2→4 — the headroom test and the budget test both **run and pass green against a 25-byte stub**, with every other bundle absent and hitting the `continue`. That is verbatim CLAUDE.md's "an environment-suppressed assertion is a passing test that proves nothing", and it falsifies the adjacent comments at `bin/site.ts:439-441` and `src/entries.test.ts:304-308` ("the suite's copy can't run during a build" — it runs, it just measures nothing).

Net: no lane the release checklist executes (`bun run build`, `bun run test:browser`) ever measures headroom against artifacts the build just produced. The three tight budgets this diff raised were found by a standalone `bun test`, not by a build. That is the 1.10.0/main.js-17-bytes pattern the assertion's own comment cites three occurrences of.

**Fix:** move the `MIN_HEADROOM` check into the `BUILT` loop in `bin/site.ts`, beside the existing over-budget throw, where real artifacts exist (warn-not-throw is acceptable if a hard mid-release failure is unwanted). Keep the suite copy for local runs, but note that **removing the `skipIf` would not fix it** — it would only make the vacuous run unconditional. Reconcile the two contradicting comments while there.

### M2 — A string `content` in a shadow-DOM component erases the component's own stylesheet
`src/component.ts:2745` · lens correctness · **verified/confirmed**

The normalisation guard excludes `typeof _content !== 'string'`, so a bare string is the one single-value content never passed through `applyPositional`. It reaches `src/dom.ts:260-261`, which does `elt.textContent = content` — on a ShadowRoot that replaces **all** children including the `<style>` node appended two lines earlier (`src/component.ts:2796-2805`).

Probed (shadow components with `static shadowStyleSpec`; `<style>` count):

```
content = 'hi'                -> "hi"                    styles: 0   BROKEN
content = () => 'hi'          -> "hi"                    styles: 0   BROKEN
content = 42                  -> "<style>…</style>42"    styles: 1
content = 10n                 -> "<style>…</style>10"    styles: 1
content = ['hi']              -> "<style>…</style>hi"    styles: 1
content = document.createTextNode('hi')                  styles: 1
```

String is the sole outlier, **because of the clause this commit wrote**: number/bigint used to throw and now work; string silently wiped the stylesheet and still does — an inconsistency introduced into the very branch being normalised. `string` is a first-class member of `ContentPart`, and the new doc table says "A single non-array `content` is classified the same way" — demonstrably false for a string.

Mitigating: the defect is pre-existing, and no consumer of it exists today (grep over `src/` and `../tosijs-ui/src` finds no component pairing a bare-string `content` with a `shadowStyleSpec`). Severity held at major on failure mode — silent, total style loss, no warning, no throw, on a documented and type-legal input.

**Fix:** drop `&& typeof _content !== 'string'` from the guard so strings take the `applyPositional` → array → `append()` route (probed safe; matches the `['hi']` result). Alternatively make `appendContentToElement` append a text node rather than assigning `textContent`. Then correct the doc line and the reasoning in the `src/dom.ts:244-250` comment (its conclusion is type-accurate; its stated reason is wrong for the string case).

*Re-review scope if fixed: correctness over the remediation diff plus a full `src/component.test.ts` run — the string path is widely used.*
