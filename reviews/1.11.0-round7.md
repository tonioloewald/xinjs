## Blockers (fix before tag)

### B-1 — the new wrapping-`<label>` step REPLACES the one-step-up harvest, regressing label-bound controls from `⟨secret⟩` to cleartext
`src/agent.ts:1400-1412` · lens: correctness · **verified**

`refreshSecretPaths` used to read `el.parentElement`. It now reads `stepFrom.parentElement`, where `stepFrom` is the wrapping `<label>` when there is one — so the label's **own** bindings are never consulted.

Measured, base `e8964d6` vs HEAD, happy-dom and real Chromium against the shipped `dist/module.js`, posture `expose: { roots }`:

- `label({ bindValue: a1.pw }, 'Password ', input({ type: 'password' }))` → base `read('a1.pw') === '⟨secret⟩'`, `describe()` clean; **HEAD returns the cleartext password and `describe()` publishes it.**
- `div({bindValue}) > label > input[type=password]` → base cleartext, HEAD `⟨secret⟩` (the intended new coverage).

A straight trade, in the function this release is named for, in the round convened specifically to stop over-claiming coverage. The shipped artifact carries it (`d=t.parentElement;if(d!=null&&d.tagName==="LABEL")c=d;let u=l?c?.parentElement??null:null`). Zero tests in the repo put a binding on a `<label>` — `grep -n 'elements.label' src/agent.test.ts` returns four hits, none with a bind prop — so the whole suite is green over it. The new leak is **not** in the CHANGELOG's "Still NOT covered — verified leaking at this tag" list (`CHANGELOG.md:140`), and the same entry's "this is a fix, not a regression" / "never worse than 1.10.1 at any point" are both now false for this shape.

**Fix:** make the step **additive**. Harvest from `el.parentElement` **and**, when that parent is a `LABEL`, from `wrappingLabel.parentElement` — a small candidate list run through the existing `fromDOM != null` loop, deduped against `owningForm` (which already compares `!== parent`). The verifier patched exactly this into a scratch copy of HEAD: both shapes return `⟨secret⟩` and `src/agent.test.ts` passes **113/113**, including all four deliberate over-redaction controls. The trade was never forced.

**Pin:** the regression control (binding on the wrapping label → `⟨secret⟩`, token absent from `JSON.stringify(describe())`) placed beside the round-6 label test, so both directions are pinned together.

**Re-review scope:** correctness + security over the remediation diff only; re-run all four over-redaction controls in the `#41` describe block plus the new label pair. `secretPaths` is append-only, so over-redaction is a permanent availability break.

### B-2 — `describe()` publishes `checked: true` for a path `read()` refuses, because the guard that would strip it sits behind `record.text === undefined &&`
`src/agent.ts:2455-2462` · lens: security · **verified** · *(round-5 B-1 / round-6 B-4, still unfixed)*

Posture `expose: { roots }` — not `expose:'all'`. Two checkboxes on the same path, one carrying `data-tosi-secret`, the other additionally carrying a text binding:

```
agent.read('v3.twoFactor')  →  "⟨secret⟩"
agent.describe().wiring[1]  →  {"tag":"input","type":"checkbox","checked":true,
                                "value":"⟷ v3.twoFactor","text":"mirror ⟵ v3.caption"}
```

The record discloses through one channel exactly what it withholds through the other, and carries no `secret: true` to say anything was withheld. `record.checked` is written unconditionally at `src/agent.ts:1811-1814`; the only thing that strips it for **path**-derived secrecy is `delete record.checked` inside `suppressHarvest` (`:1635`) — which a defined `record.text` short-circuits before it is ever called. Reachable through `tosi_describe`, which `src/webmcp.ts:105-116` registers unconditionally, while `tosi_read` sits behind `canRead`: **the ungated tool hands over what the gated one refuses.**

This is a remediation composed onto a pre-existing fail-open gate. `src/agent.ts:1618-1634` affirmatively ships the claim it defeats — "a live-state field added later inherits the guard by construction instead of needing a tenth gate." It inherits it only when the author's markup happens to carry no text binding. The existing B-1 pin (`src/agent.test.ts:3093`) uses a bare mirror with no text binding and passes either way.

**Fix:** call `suppressHarvest(el, record, allBoundPaths)` **once, unconditionally**, immediately after the data-binding loop, and consume its boolean in the three harvest conditions — so "does this record already have text/value" becomes a separate question from "may this record carry content". The two sibling sites (`contenteditable` behind `record.value === undefined` at `:2476`, structural tier behind `heading &&` at `:2713`) have the same shape and should move to the same choke point. Pin with the `bindText`+`bindValue` checkbox fixture.

**Re-review scope:** security + correctness over `recordFor`'s harvest conditions and `suppressHarvest` only; confirm all four over-redaction controls still pass and no record loses a legitimately-published `text`/`value`.

## Majors (not blocking the tag, but decide them before it)

### M-1 — `describe()` publishes a password in cleartext inside the very record it stamps `secret: true` *(round-6 B-1, silently dropped from the remediation)*
`src/agent.ts:2382` · security · **verified**

Posture `expose: { roots }`: `div({bindValue: v1.pw}) > div.row > input[type=password]` → `wiring: [{"tag":"div","value":"CLEARTEXT-V1 ⟷ v1.pw","secret":true}]`. Same for `form({bindValue: v2.tok}) > div > <v-field data-tosi-secret>`. Ordering: `recordFor` calls `boundValue(b.path, twoWay, record.secret === true)` at `:2382` while `record.secret` is still only the element-or-ancestor answer; `suppressHarvest`'s containment arm sets `record.secret = true` 75 lines later at `:2457`. JSON key order confirms it (`value` serialized before `secret`).

This violates the shipped public contract: `dist/agent.d.ts:218` documents `secret` as "its VALUE is never emitted, only the fact that it exists and what it's bound to." `src/audit.ts` contains zero occurrences of `secret`, so a consumer has nothing but the label to trust. Commit `50835b2` landed round-6's B-2 and B-3 and dropped B-1 and B-4 with **no keep-decision** anywhere.

**Fix:** ask the containment question once before the binding loop — `const contentSecret = harvestWouldLeak(el, record, allBoundPaths)` (pure, does not mark) — and pass `record.secret === true || contentSecret` as `boundValue`'s third argument. **Do not** assign it to `record.secret`: `:2379`'s `if (record.secret === true) addSecretPath(b.path)` is the round-4 path-poisoning route and must keep seeing element-or-ancestor secrecy only. Verified that `harvestWouldLeak` returns true for both fixtures before the loop, so this closes the `describe()` half of two of the three shapes the CHANGELOG lists as leaking. Pin both repros asserting the token is absent from `JSON.stringify(describe())`, keeping the round-4 control (`read('c41a.theme') === 'dark'`) beside them.

### M-2 — `refreshSecretPaths` fails **OPEN** when its DOM scan throws: one element with a throwing accessor silently disables further redaction, document-wide
`src/agent.ts:1244-1250` · security · **verified**

A sibling carrying a throwing `shadowRoot` accessor — or a **real** `attachShadow` root whose `querySelectorAll` throws — flips `agent.read()` from `⟨secret⟩` to cleartext. `deepQueryAll` reads `(el as any).shadowRoot` for every element; the `try` wraps the whole O(document) walk and its `catch (_e) { return }` learns nothing, with no warning and without consulting `settings.quiet`.

Every sibling guard in this file catches in the **opposite** direction and says so: `referencedNodeIsSecret` (`:888`) and `harvestWouldLeak` (`:1674`) both `catch { return true // cannot tell === must not publish }`. This one alone answers "cannot tell" with "nothing is secret". The comment's stated rationale ("a DOM shim without full selector support") covers only the first statement — `SECRET_CONTROL_SELECTOR` is plain CSS2/3, so the documented trigger is the least likely one and the reachable triggers are the two per-node accessors the catch silently also covers.

Precision refinement (not a defeater): `secretPaths` is append-only, so paths learned before the throwing node appears stay redacted; the accurate statement is "all **further** secret-path learning stops, document-wide". In the ordinary case (a component present at load, before `enableAgentInterface()`), nothing is ever learned and the headline is literally correct.

Separately, the diff adds two unguarded reads into the same unprotected loop body (`el.getAttribute?.('autocomplete')` at `:1365`, `el.parentElement.tagName` at `:1401`); a throwing `parentElement` getter there propagates **uncaught out of the public API** (`THREW: boom-parent`). Fail-closed, but an unhandled throw from `read()`.

**Fix:** (1) isolate per node — wrap each shadow-root recursion in `deepQueryAll` in its own try/catch, and wrap the per-candidate body of the `for (const el of candidates)` loop so one bad node cannot abort learning for later candidates. (2) Make total failure **loud and closed**: on a top-level scan failure set a module flag that makes `isSecretPath`/`containsSecret` withhold, or at minimum emit a non-suppressible `console.warn` naming the surface as unredacted. Add both hostile fixtures (throwing `shadowRoot`, throwing `form`). No coverage exists today — `grep shadowRoot src/agent.test.ts` returns nothing.

### M-3 — the release publishes a security coverage matrix derived entirely from happy-dom, and at least one entry is a shim artifact
`CHANGELOG.md:126-150`, `src/agent.test.ts:3374` · blast-radius · **verified in real Chromium**

Measured in Chromium against the committed `dist/module.js`:

```
ce.parentElement === form                                     : true   (false in happy-dom)
CE[data-tosi-secret] DIRECT child of bound form               : ⟨secret⟩   ← covered
CE two levels under bound form                                : leaks
shadow component w/ password inside bound form                : leaks
div(bindValue) > div > input[type=password]                   : leaks
el.form arm at depth / wrapping <label>                       : ⟨secret⟩   ← honest
```

So `CHANGELOG.md:139-142` — "a custom element carrying `data-tosi-secret` inside a bound `<form>` … **the worst shape on this list**" — **is wrong as written**: the direct-child case is covered in a real browser by the one-step parent arm, and the stated cause (`el.form` undefined on a custom element) applies only at depth. The "explicit author marker is weaker than the heuristic" claim survives only for the deeper shape. The other two "Still NOT covered" entries are honest, and the two riskiest "Now covered" entries hold in Chromium — so no leak is *under*-reported; the harm is wrong worst-shape ranking and wrong mitigation advice.

**And the hole generalises past "custom element", which the CHANGELOG does not say:** a plain `<div data-tosi-secret>` region two levels under a bound form also reads **cleartext** in Chromium, while the same region as a direct child reads `⟨secret⟩`. The shipped mitigation sentence — "Marking the control itself **or its immediate region** works in all of these" — is therefore false for a region at depth. Fix it in the same CHANGELOG pass B-4 already requires.

**Second-order cost, the sharpest part:** a happy-dom artifact *steered a design decision*. `el.form` was chosen over `closest('form')` because of the wrapper-identity quirk (`src/agent.ts:1434-1445` says so), and `el.form` is exactly what leaves author-marked non-controls uncovered at depth in real browsers. `closest('form')` — wrong only under the shim — would have covered them. The witness that cannot be trusted picked the arm.

**Fix:** add the light-DOM `#41` shapes (covered *and* leaking) to `tests/shadow-secret.pw.ts`, run `bun run test:browser`, re-derive the matrix from that lane, and correct every entry the browser disagrees with before tagging. Cheap version if the lane is deferred: state in the CHANGELOG that the matrix is measured under happy-dom and name the shim-sensitive entries. Reconsider the `closest('form')` fallback for custom elements now that its only counter-evidence is known to be a shim defect.

### M-4 — a happy-dom node-identity defect is absorbed as a code comment instead of filed upstream, and the durable record of it is wrong
`UPSTREAM.md` (no happy-dom section — `grep -ci happy-dom UPSTREAM.md` = **0**) · blast-radius · **verified**

happy-dom 20.11.1 returns `new Proxy(this, …)` from the `HTMLFormElement` and `HTMLSelectElement` constructors while parent/child links hold the raw target. Measured: a `<div>` chain preserves identity at every level, but `outer.parentElement === form` is **false**, `input.closest('form') === form` is **false**, `opt.parentElement === sel` is **false**; `input.form === form` is true.

Materiality is broader than the secrecy path: bindings are WeakMap-keyed on element identity (`src/metadata.ts:384`), so `getElementBindings(pw.closest('form'))` returns **0** while `getElementBindings(pw.form)` returns 1 — and `elements.form({onClick})` containing a button fires the delegated handler **0 times** on a bubbling click where the `elements.div` twin fires once. Any ecosystem test asserting a form-level handler passes vacuously — exactly the "environment-suppressed assertion" class CLAUDE.md warns about. tosijs-ui peers happy-dom `^20.7.0` and consumes tosijs's element-keyed metadata; nothing about this is recorded in `../tosijs-coding-practices`.

**One correction to the finding as filed:** `CHANGELOG.md:135` is accurate and correctly narrow. The overgeneralised sentence is in **production source**, `src/agent.ts:1439-1441` — "closest('form'), a manual parent walk and even `parentElement.parentElement` all return distinct wrapper objects for the same element" — which is false for ordinary containers and misleading in the worst direction, because the one-step parent arm 30 lines earlier depends on precisely the identity that comment declares broken.

**Fix:** file upstream against happy-dom with the four-line repro; add the `UPSTREAM.md` section (version + workaround + issue URL); narrow `src/agent.ts:1439-1441` to the measured fact (form/select parents only); add the bullet to CLAUDE.md's "Happy DOM limitations" list and to the shared KB. Round 6 already asked for this filing and `50835b2` did not do it, with no carryover item — so it is currently unactioned with nothing pointing at it.

### M-5 — upward secrecy propagation is now three arms plus a fourth spelling of the predicate, with no keep-decision — and drift between two spellings is what this diff was fixing
`src/agent.ts:1304-1307`, `:1408-1411`, `:1450-1453`, predicate at `:1366-1371` vs `isSecretControl` at `:1550` · blast-radius · **verified**

The four-line harvest (including the load-bearing `if (b.binding?.fromDOM != null) addSecretPath(b.path)`) is byte-identical at three sites. `v1.10.1` had **one**; this release tripled it (`812cefa` added the parent arm, `84e701a` the form arm). Two measured drift incidents in this subsystem, one a confirmed cleartext leak.

Round 6 asked for `propagateSecrecyTo(node)` + one predicate **or** an explicit keep-decision; `50835b2` did neither, and `TODO.md:21-24` still frames the shadow/light asymmetry as an open question, not a decision. Forward cost is concrete: each of the three still-leaking shapes needs multi-arm edits, and the shadow-inside-form case would require a **fourth** copy.

**Fix:** extract `propagatesSecrecyUpward(el)` and `harvestFromDOMBindings(node)` and call them from all three arms. If deferred, record the keep-decision in `TODO.md` naming the shipped hazard — a structural twin on a security path cannot be deferred silently.
