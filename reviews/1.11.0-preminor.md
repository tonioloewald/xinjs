## Majors — both upstream-gated, neither fixable in this repo this release

### M1 — correctness — a list-bound element that IS the control is now audited as structure, silencing two error-severity rules

`src/schematic.ts:298` (vendored) · consumed at `src/audit.ts:184`

`isGround = (w) => w.structural === true || (w.list != null && w.on == null)`, and `isInteractive` short-circuits on it. `select({ bindList: {value: app.options, idPath: 'id'}, bindValue: app.choice }, …)` describes to `{tag:'select', list:{…}, value:'b ⟷ app.choice', bounds: 20×20}` with no `on` — so it is ground, and `isInteractive()` is false. Measured, old predicate vs HEAD over identical records:

| record | 1.10.1 | HEAD |
| --- | --- | --- |
| list-bound `<select>` + `bindValue`, 20×20 | `[target-size]` | `[]` |
| nameless, role-less list-bound `<div>` with a two-way arrow | `[anonymous-affordance, missing-role, target-size]` | `[]` |
| list container **with** `on` | unchanged | unchanged |

`interactive` gates `anonymous-affordance` (**error**) and `missing-role` (**error**) as well as `target-size`, so two error-severity rules go silent. The CHANGELOG's justification ("its *items* are the affordances") is right for a `<ul>`/`<tbody>` and over-broad for an element that is both container and control — the `<option>` records in the same map carry 0×0 bounds and are not separately hittable. This combination is not exotic: **1.10.1's own M1 fix** (`src/elements.ts:764`, "a container can be list-bound *and* carry its own binding") exists specifically to enable it.

**The rule is untested.** `src/audit.test.ts:319` pins it with a record whose evidence sits in `label` — which is in the new `NEVER_BOUND` set — so the test passes identically with the list clause deleted. Nothing in the suite exercises the shape tosijs actually emits.

Not a blocker: `auditAccessibility` is EXPERIMENTAL and opt-in, nothing corrupts state, and the fix has to land in tosijs-floorplan and be re-vendored.

### M2 — security — a map can silence the audit's own target-size rule, including the audit's own output fed back through the documented flow

`src/audit.ts:233` → `src/schematic.ts:348-353`

1.10.1's audit did its own geometry and ignored `flags`. HEAD delegates to `targetSizeFinding`, which returns `null` whenever `w.flags` contains any flag whose `kind` lowercased contains `"target"`. Probe:

```
button, on.click, label 'Go', 10×10        -> ["target-size"]
  + flags:[{kind:'target-size'}]           -> []
  + flags:[{kind:'target-ok'}]             -> []
  + flags:[{kind:'TARGETS ARE FINE'}]      -> []
  + flags:[{kind:'contrast'}]              -> ["target-size"]   (control)
auditFlags(base) merged into wiring[0].flags, re-audited -> []
```

Two paths. **(a) Self-defeating round trip:** `auditFlags()` emits `kind: finding.rule` — literally `'target-size'` — and `schematicSVG` has *no* `flags` option, so the documented workflow (`src/audit.ts:34`, "hand the pair to `schematicSVG`'s `flags` to *draw* them") can only be implemented by writing findings onto `wiring[i].flags`. Any tool that draws findings and re-audits gets a clean verdict on the elements it just flagged. **(b)** A foreign map — the explicitly supported case — disables the rule with one substring match on data it authors.

The sharpest point: the renderer's rationale ("no double amber bars") is sound *because the producer's flag is still drawn*. In the audit the compensating half is missing — `auditAccessibility` never reads `w.flags` into `findings`. A **well-behaved** producer shipping a genuine undersize finding via `flags` gets a report with no target-size finding at all. This is not merely a trust-the-input complaint.

Undisclosed and unpinned: this is a **seventh** verdict change; the CHANGELOG enumerates six and claims all six are pinned. No test in `src/audit.test.ts` passes a `flags` array at all. tosijs's own `describe()` never emits `flags`, which bounds the blast radius to foreign maps and draw-then-re-audit tooling.
