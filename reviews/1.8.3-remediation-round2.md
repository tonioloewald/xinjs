## Blockers

### B1 — `bind` clobbering was fixed in `create()` but not at its second address, `Component.hydrate()`

`src/component.ts:2423` · lens: correctness · **verified (reproduced, happy-dom, HEAD)**

`hydrate()` folds plain-object content items into host props with a bare `Object.assign(hostProps, item)`. Since `.tosi.listBinding()` switched from `{ bindList }` to `{ bind }` (in `d459382`, not in v1.8.2), two `bind` keys now collide and last-write-wins:

```
ORDER A (listBinding first, caller's bind second):  rows=0   data-title=hello   ← the ENTIRE LIST vanishes, <template> unconsumed, no error
ORDER B (caller's bind first, listBinding second):  rows=2   data-title=null    ← the caller's binding silently dropped
CONTROL (listBinding alone):                        rows=2
```

The identical construct through `elements.div(...)` passes both assertions — commit `f4980bf` fixed exactly this in `src/elements.ts:756-780` (accumulate `bind` into an array) and added tests **there only**. `git diff v1.8.2..HEAD --stat` confirms `src/component.ts` was never touched. Host props in a content array are a documented feature (`src/component.ts:122`) whose doc promises the props apply "just as they would be applied to the element being created by `div()`" — that promise is now false.

**Fix:** extract one `mergeElementProps(target, item)` helper and call it from both `create()` (elements.ts:756-780) and `hydrate()` (component.ts:2423), so the two addresses cannot drift a third time. Add both-order component tests mirroring the `src/xin.test.ts` "a container can be list-bound AND carry its own bind (review M1)" block.

### B2 — The M4 secret-redaction fix covers only the id-path spelling; a list _without_ `idPath` still hands back every secret it contains

`src/agent.ts:760-766` · lenses: correctness + blast-radius (deduped) · **verified (reproduced against `src/`, read-only default posture)**

`redactWithin` descends arrays by id-path only when `getArrayIdPaths(path)` yields one. Without a registered `idPath` — a documented, supported configuration (`src/list-binding.ts:119`, "Skipping idPath is fine when…") — `ListBinding` names rows `${arrayPath}[${i}]` while the walk builds `${path}.${key}`. `extendsPath` is a pure string prefix test, so nothing matches and the walk never descends:

```
read('nl.rows[0].pw') -> "⟨secret⟩"
read('nl.rows')       -> [{"id":"r1","label":"work","pw":"hunter2"}]   ← the exact bug M4 was written to fix
read('nl')            -> leaks too
```

Second variant, also verified: when two list bindings register **different** idPaths for one array, `[...idPaths][0]` picks one and secrets under the other spelling come back cleartext (`read('two.rows')` → `pw:'p2'`).

This is reachable through **`describe()`** as well, i.e. through `tosi_describe` — the one WebMCP tool published in _every_ posture — the exact B1 shape this release exists to fix. Precise reachability: a list binding alone does not leak via describe (`record.list = …; continue` short-circuits before `boundValue`), but as soon as any non-list element binds the array or an ancestor, `JSON.stringify(agent.describe())` contains the cleartext secret. Also verified: with `idPath` present, `read('sl.rows[0])` still returns the whole row cleartext.

The comment now at `src/agent.ts:617-619` asserting _"Reading the PARENT array is now safe (redactWithin descends by id-path)"_ is **false** for both variants and will misdirect the next reader.

**Fix:** in `redactWithin`'s array branch, test every spelling that can name the item — `${path}[${key}]` (bracket index, the spelling bindings actually register) **and** every registered id-path form (iterate the Set, don't take `[0]`). Redact if any spelling hits `isSecretPath`; recurse under the one that hits `containsSecret`. Add tests for the no-idPath list at item / array / root level, through `describe()` and `changes()`, and correct the in-source comment to state what is and is not covered. (Credit where due: the _query_-side gap was routed properly — issue #32 carries a repro, root cause, fail-closed requirement and a test plan. This finding is that the _descent_ side the commit claimed to fix is still half-open, and the fix is adjacent and cheap.)

### B3 — New crash introduced by the M4 fix: a `null` element in an id-path array makes `read()`, `describe()` and `changes()` all throw

`src/agent.ts:765` · lens: correctness · **verified (reproduced)**

`const idValue = idPath != null ? getByPath(clone[key], idPath) : undefined` passes `clone[key]` unguarded. `getByPath`'s walk guards `found !== undefined` only, so `getByPath(undefined, 'id')` is safe but `getByPath(null, 'id')` throws `TypeError: null is not an object (evaluating 'found[key]')` (`src/by-path.ts`).

With an `{ idPath: 'id' }` list containing a secret-bound control, `rows = [{id:'a',pw:'p1'}, null]` (a sparse page, a cleared row, a server payload with a hole) makes `agent.read('nl.rows')` and `agent.changes(0)` throw — and `changes` throws _inside the coalescing loop_, so every subsequent poll dies once a null lands. `describe()` throws too when an element binds the array path itself. No `try/catch` wraps `redactWithin` at any of its three call sites (agent.ts:955, :1179, :1771). `git show 147cf5e:src/agent.ts` confirms the pre-M4 body had no `getByPath` call — this path did not exist before `9053066`.

It fails **closed** (throws rather than leaking), so there is no additional security exposure — but `tosi_describe` is published in every posture, so one null row takes the agent surface down for the page.

**Fix:** `clone[key] == null ? undefined : getByPath(clone[key], idPath)`, and separately consider widening `getByPath`'s guard to `found != null` since it is a public export. Add a test with a null row covering read / describe / changes.

### B4 — Release identity is still 1.8.2, and the committed `dist/` predates the security commit entirely

`package.json:3`, `src/version.ts`, `CHANGELOG.md:9`, `dist/*` · lenses: correctness + blast-radius (three findings deduped) · **verified (git + artifact execution)**

Three compounding facts, each independently confirmed at HEAD with a clean working tree:

1. **Identity.** `package.json`, `src/version.ts` and the newest CHANGELOG heading all read `1.8.2`. `npm view tosijs version` → `1.8.2`. `agent.describe().version.tosijs` prints `1.8.2`. Yet `git diff --stat v1.8.2...HEAD -- src/` is 10 files / 645 insertions. Any consumer bug report, `agent.version` check, or debug-bundle banner names a build that does not exist on npm.
2. **Stale artifact — the tested copy is not the shipped copy.** `git log -- dist/` → newest dist-touching commit is `147cf5e`. `git show --stat 9053066` lists exactly two `src/` files and no bundles. Confirmed by content, not just metadata: `grep -c getArrayIdPaths dist/module.js` → **0** (`src/agent.ts` → 2), and executing the committed `dist/module.js` under the SEC-2c scenario yields `read('sl.rows')` → `[{"id":"r1","label":"work","pw":"hunter2"}]` **cleartext**, while the same scenario against `src/` yields `⟨secret⟩`. `files` publishes `/dist` verbatim; `prepublishOnly` is `bin/check-publish-tag.ts`, which does not build; `.github/workflows/ci.yml` runs `bun install / bun test / playwright` with no build and no freshness check. `npm publish` from this HEAD ships a bundle **without the security fix its own commit is named for**. Because `dist/` is deliberately committed and `9053066` is already on `origin/main`, any git-ref or CDN consumer of `main` gets the vulnerable build today.
3. **No consumer-visible record.** The unreleased delta contains four observable changes with no line anywhere: `.tosi.listBinding()`'s returned props key changed `bindList` → `bind` (so `props.bindList` is now `undefined` — this repo's own tests had to be rewritten); `ElementProps.bind` widened to accept an array (ships via `dist/xin-types.d.ts`); all four `bind*` deprecation messages rewritten; two secret-leak fixes. `CHANGELOG.md:200` already tells readers _"If you are relying on the agent surface's redaction guarantees…"_ — redaction is an advertised, relied-upon property, and the CHANGELOG is the only doc in the tarball.

**Fix:** bump to `1.8.3` in `package.json` (which stamps `src/version.ts`), write the `[1.8.3]` CHANGELOG section covering the four items above **and** stating the residual redaction gap with a link to #32, then `bun run build` + `bun run test:browser` and commit regenerated `dist/` + `docs/`. Re-run the dist-level security probe against the regenerated bundles rather than trusting the unit suite. Headroom is comfortable against the raised budgets (Bun-zlib: index 29.0k/30k, module 42.0k/43k, main 42.3k/43.5k, core 26.4k/27.5k).

> Note for the re-review: the regenerated `dist/` will be an artifact no lens has read, and it will change security-relevant behaviour. Scope the re-review to executing B2/B3/B4 scenarios _from the bundles_.
