## Blockers

### B1 — The 1.10.1 CHANGELOG entry opens "Type-only. No runtime change, no bundle change." above a section documenting exactly those changes
`CHANGELOG.md:11` *(verified; reported independently by correctness and blast-radius, deduped)*

All three clauses are false, and the contradiction is four lines away:

- **"Type-only"** — `git diff 3a242c1...HEAD -- src/elements.ts` is an 87-line rewrite of the positional-argument dispatch in `create()`, the most-used API in the library: two new predicates (`isPropsBag`, `renderableAsText`), a text-child branch, an array-warning branch, and a new `console.warn` in the props branch.
- **"No runtime change"** — verified by *executing both artifacts*, not by reading the diff. `git show 3a242c1:dist/module.js` renders `div(new Date(0))`, `div(10n)`, `div(false)` as `<div></div>` and `div([a,b])` as `<div 0="<span>a</span>" …>`. HEAD's `dist/module.js` renders the date, `10`, `false`, and warns on the array. The committed `dist/` genuinely carries the new code.
- **"no bundle change"** — `bin/bundles.ts` raises `module.js` 43_500→45_000 and `main.js` 44_500→46_000 for a stated "+264 gz"; `README.md`'s generated sizes block moved ~42 kB → ~43 kB in the same diff.

Provenance is plain staleness: the line was written in `7dd02d1` where it was accurate; `b04caf9` appended the `### Changed` section beneath it and did not touch it. `CHANGELOG.md` is in the published `files` array, so this reaches npm consumers. `div(false)` now emitting literal `"false"` is precisely the visual regression class the headline sentence tells a reader they may skip re-checking — and tosijs-ui, mid-adoption of 1.10.x, is the reader who would take it blind.

The prior review (`reviews/1.10.1-preminor.md:76`) already carries this item, but on the now-obsolete `+6 bytes raw` basis and with a proposed reword — "Behaviour is identical" — that would write a **second** false statement if applied verbatim. Rewrite from scratch.

**Fix (one sentence, mechanical):** e.g. *"Type fix plus a deliberate change to how positional arguments to element creators are dispatched; `dist/` and the gzip budgets changed (+~290 gz per bundle)."* Also correct the stale entry date (`2026-09-04`; work ran through 09-06).

**Re-review scope: Tier 0 only** — *unless* the majors below are also remediated, in which case `src/elements.ts` needs a correctness pass.

## Majors (confirmed; unresolved — these are why the verdict stays BLOCK even after B1's one-line fix)

### M1 — A function passed positionally renders its own source code into the DOM, silently
`src/elements.ts:614` *(verified; two lenses, deduped — severities split major/minor, taken as major)*

`isPropsBag` opens `if (typeof item !== 'object') return false`, so a function is never a props bag; `renderableAsText` then passes because `Function.prototype.toString !== Object.prototype.toString`. Measured at HEAD, **zero warnings** in every case:

- `div(() => 42)` → `<div>() =&gt; 42</div>` (base: `<div></div>`)
- `div(elements.span)` (forgotten `()`) → `<div>(...contents) =&gt; create(tagName, ...contents)</div>`
- `div(class Foo { secret() { return 'API_KEY_123' } })` → the whole class body, including closure literals, painted into the page and into prerendered HTML

The release is titled "values render, `Map` applies, **mistakes complain**" and complains correctly for the neighbouring mistakes (`div(Promise.resolve(1))` warns, `div([1,2])` warns) — but stays silent for the callable one. The diff's own gate at `src/type-surface.test.ts:57` carries `// @ts-expect-error a bare function is not an element part`, so the types reject what the runtime renders. TypeScript blocks the typed spellings (TS2345 verified), so exposure is untyped consumers — the IIFE/CDN bundle, plain JS, doc-site live `js` fences, and `any`-typed call sites — which this library markets to.

**Fix:** `if (typeof item === 'function') return false` in `renderableAsText`, so functions fall to the existing "neither a child nor a props object" warning. Add the runtime test.

### M2 — The contents dispatch drifted again: the `<div 0="…">` bug the CHANGELOG calls fixed is live at the second address
`src/component.ts:2719` *(verified)*

`create()` (`src/elements.ts:760-847`) and `Component.hydrate()`'s content-array filter (`src/component.ts:2714-2736`) are the two addresses that `mergeElementProps` was extracted to keep in step — its doc comment says so in as many words. The new dispatch landed at one of them. Reproduced:

- `content = [span('a'), new Date(0), 10n, false]` → `<drift-one><span>a</span></drift-one>` — Date, bigint and boolean vanish, **no warning**
- `content = [span('a'), [span('b'), span('c')]]` → `<drift-two 0="<span>b</span>" 1="<span>c</span>">` — verbatim the symptom the release notes hold up as fixed, **no warning**

The two copies also disagree about `Node`: `hydrate()` tests `item instanceof Node` (correct), `create()` tests `Element || DocumentFragment` (narrower). `ContentType` is `Element | DocumentFragment | string`, so both repros are TS2416 for typed consumers — live exposure is vanilla JS, blueprint-supplied content, and `any`. Not a regression from this diff; the diff widened an existing gap while claiming to close it.

**Fix:** extract the *classification* (child / text-value / array-mistake / props / neither) next to `mergeElementProps` and call it from both sites. Pin with a test that runs one argument set through `div(...)` and through a component `content` array and asserts identical outcomes.

### M3 — `div(app.someArray)` regressed to warn-and-drop, and `isPropsBag` went O(N) on the same argument
`src/elements.ts:795` and `:610` *(verified; three lenses, deduped — efficiency confirmed major, blast-radius downgraded to minor; taken as major because both halves share one fix)*

`Array.isArray()` is true through the proxy, and the new array branch at `:795` sits **above** the `tosiPath(item)` branch at `:809`. Measured base vs HEAD on the same proxied array:

- base → `<div><span class="-tosi-data">x,y</span></div>`, live (`push('z')` + `touch()` → `x,y,z`)
- HEAD → `<div></div>` + *"did you mean to spread it?"*

Compounding it, `isPropsBag` falls past both short-circuits for an array-backed proxy to `Object.keys(item).length > 0`, materialising one index string per element. Measured µs/call: base flat at ~1.6 across n=0…20 000; HEAD 1.7 / 0.65 / 1.94 / 14.3 / 276 / **1563**. With the real `console.warn`, one such call costs **3.3 ms** and dumps the whole array to the log (retained against GC in devtools). Ordinary argument forms are unaffected (props bag, object proxy, scalar proxy all short-circuit at `proto === Object.prototype`; measured unchanged).

The contradiction is internal: `src/xin-types.ts:412` widened `ElementPart` to `TosiProps<any>` in *this diff* with the rationale "covers object and array proxies", and `tsc` confirms `div(app.list)` compiles clean — the type says yes, the runtime says forgotten spread. Nothing tests either behaviour. Mitigating: the lost output was `String(array)` comma-joined text (junk for object arrays), it is announced by a warning, and no call site of this form exists in tosijs, its docs, or tosijs-ui.

**Fix (two one-liners, both halves):** `if (Array.isArray(item)) return false` as the first test in `isPropsBag`; hoist the `tosiPath(item)` branch above the `Array.isArray` branch. Truncate the `console.warn` payload. If the drop is kept deliberately for proxied arrays, the message must name the real idiom (`.tosi.listBinding(...)`), and the CHANGELOG must say so.

### M4 — `AgentPathRef` has collapsed to `any`, one address over from the defect this release was cut to fix, and the new gate passes green
`src/agent.ts:555` *(verified)*

`export type AgentPathRef = string | BoxedProxy<any> | BoxedScalar<any>`. `any` distributes through `BoxedProxy`'s conditional (`T extends Function ? T & TosiProps<Function>`) and that branch yields `any`, so the union is `any`. (`BoxedScalar<any>` does *not* collapse — its fallback is `unknown`.) Verified with `tsc --strict` against the shipped declarations: `IsAny<ElementPart>` is now `false` (the release's fix works) but `IsAny<AgentPathRef>` and `IsAny<AgentObserveRef>` are `true`, and `const a: AgentPathRef = 12345 | () => {} | { nonsense: true } | null` all typecheck.

This is the declared parameter type of `read`, `write`, `call`, `when`, `observe`, and `expose.roots`/`expose.actions` — the entire agent entry surface has no compile-time checking. Runtime `toPath()` refuses with a good message, so the cost is lost checking rather than a wrong result. Not a regression (`src/agent.ts` is untouched in this diff; it shipped `any` from birth), and the anti-`any` gate does not falsely claim coverage — it simply doesn't cover this type. The warning against exactly this pattern is written one file over at `src/xin-types.ts:402-413`.

**Fix:** `| TosiProps<any>` for `| BoxedProxy<any>`, and extend the gate to iterate the anti-`any` assertion over every name the export-surface list already enumerates, so a third site cannot hide.

### M5 — A runtime dispatch change is shipping as a PATCH, and the downstream it exists to unblock has never been built against it
`CHANGELOG.md:13` *(verified)*

1.10.1 was scoped as a type-only fix for tosijs#38 (reported by tosijs-ui). It now also changes rendered output, adds `console.warn` to previously-silent no-ops, and **adds functionality** (`Map` as a props bag) — a SemVer minor, not a patch, under a caret range that auto-upgrades. `/Users/tonioloewald/tosijs-ui/package.json` still declares and installs **tosijs 1.9.1**: the named reporter has never compiled or rendered against this candidate.

The "React arrivals get a stray `false`" framing is partly refuted — `div(cond && child)` fails TS2345 at v1.10.0 and still does, so exposure is untyped consumers only, and `false` rendering `"false"` is a deliberate, documented divergence (not a prior-art complaint to re-litigate). What survives is release hygiene: a patch that alters output, announced by a heading that denies it, with the downstream unexercised.

**Fix:** cut as **1.11.0**. Before tagging, build and render tosijs-ui against the candidate (`practices/releasing.md` step 8c, pulled ahead of the tag as the prior review already asked).
