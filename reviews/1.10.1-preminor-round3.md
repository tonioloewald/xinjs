## Blockers

### B1 — `hydrate()` moves text-valued content to the END of the child list; `create()` renders it in place. The new regression test cannot see it.
`src/component.ts:2722, 2739, 2751` *(verified; re-reproduced during triage)*

Measured, this working tree:

```
content = [10n, span(' each')]      hydrate -> " each10"    create -> "10 each"
content = [Date, span('MIDDLE'), 'tail']
  hydrate -> <span>MIDDLE</span>tailFri Jan 02 2026 …
  create  -> Fri Jan 02 2026 …<span>MIDDLE</span>tail
```

`hydrate()` `filter`s the content array, pushing every `kind === 'text'` item into `_textFromContent` and `return false`-ing it out; line 2751 then re-appends all of them **after** every surviving child. Position is destroyed by construction. `create()` (`src/elements.ts:872-878`) appends text at its position in the single pass.

The drift only bites `Date`/`bigint`/`boolean`/`toString`-able values — plain strings and numbers classify as `'child'` and keep their slot — which is why it hides so well.

**The gate reports safety it does not have.** `src/component.test.ts:2576-2595` ("values in content render instead of vanishing") asserts only `expect(el.textContent).toContain(...)`, which passes under any permutation. There is no order-sensitive assertion anywhere in that block.

This is **not a regression against 1.10.0** — those items previously fell through to `mergeElementProps` and rendered nothing at all, so no working consumer code changes behaviour. Impact is narrow. It is a blocker on this project's definition (blocker = fix-before-tag, impact rated separately): the commit's headline claim is that one classifier makes the two sites agree, the shipped code demonstrably produces different DOM from the two paths, the fix is a couple of lines, and the test written to catch future drift is order-blind. Tagging as-is bakes in both the wrong output and a false green light.

**Fix:** replace the filter+push with a single map-style pass that emits the child list in argument order (for `'text'`, push `String(item)` at that point, or emit a `Text` node). Then assert exact `innerHTML`/child order in the test rather than `toContain` — otherwise this recurs invisibly a fourth time.

**Re-review scope:** correctness + blast radius over the remediation diff only (the hydrate content loop and its tests), plus the three majors below if they are fixed in the same pass.

## Majors (verified — resolve before tag, or record an explicit keep-decision)

### M1 — `elements.fragment()` is the third call site of the same `ElementPart[]` contract and was left on the old silently-wrong path, while this release widens `ElementPart` so the broken calls newly typecheck
`src/elements.ts:900` *(verified; two lenses deduped — reported as both a minor and a major; taken as major. Re-measured during triage.)*

`fragment` is `(...contents: ElementPart[]) => DocumentFragment` and does nothing but `frag.append(item as Node)` per argument. Exported on all three factory proxies (`elements`, `svgElements`, `mathML`). Measured against this tree:

```
fragment('a', null, 'b')   -> "anullb"          // literal "null"
fragment({class: 'x'})     -> "[object Object]"
fragment(app.name)         -> "Alice", frozen forever (div(app.name) gives <span class="-tosi-data"> and updates)
fragment([span('a')])      -> the element stringified as visible text
```

All silent. The literal `"null"` directly contradicts the contract **added in this same diff** (`src/elements.ts:64`: "`null` is the way to render nothing, and it is the only way"), under a doc line at `:252-255` saying `fragment` "is otherwise just like other element factory functions."

Not purely pre-existing: at v1.10.0 `ElementPart` excluded `BoxedScalar`/`TosiProps`, so `fragment(app.name)` was **TS2322**; this diff's widening (`src/xin-types.ts:396-410`) makes it type-legal against a function that mishandles it. Every consumer who takes the type fix is invited to write the newly-broken call. `grep fragment` over CHANGELOG.md, TODO.md and both `reviews/1.10.1-*.md` returns nothing — no decision was recorded in either direction.

Current real-world incidence is low (zero uses of `elements.fragment` in tosijs-ui's shipped `dist/`, no doc examples, one internal test) — that argues incidence, not unreality, and the type widening is what raises it going forward.

**Fix:** route `fragment()` through `classifyPositional`/`positionalWarning` — append `child`/`text`, emit the bound `span` for `proxy`, drop `null`, warn on `array`/`unusable` and on props-on-a-fragment. If deferred, say so in `TODO.md` naming `fragment`.

### M2 — a tosi proxy in a component `content` array renders a DEAD one-time string; the shared classifier labels it `'proxy'` at both sites but only `create()` acts on the label
`src/component.ts:2737` *(verified)*

`content = [span('x:'), app.user.name]` renders `<span>x:</span>Alice` and stays `Alice` after `app.user.name.value = 'Bob'; await updates()`. `div(span('x:'), app.user.name)` renders `<span>x:</span><span class="-tosi-data">Alice</span>` and updates. hydrate returns `true` for `'proxy'`, leaving the proxy in `_content`; `appendContentToElement` (`src/dom.ts:243-247`) hands a non-Node to `elt.append()`, which stringifies it once (spec behaviour, not a happy-dom artifact). Reproduced for light DOM, shadow DOM, and the function form.

Silent stale UI in an *observant* library, correct-looking on first paint, in a form the docs invite — `src/component.ts:141-143` says content-array items apply "just as they would be applied to the element being created by `div()`", and the table added in this diff says a proxy gives "a **live** child, re-rendered as the value changes."

The parity tests added in this diff cover value / nested-array / Text-node kinds and **do not cover `'proxy'`** — the one surviving divergence escapes the very test block written to catch divergence. Same root, not in the original finding: a bare non-array proxy (`content = app.user.name`) **throws** `expect text content or document node`.

Pre-existing at base (the old filter also returned `true` for `tosiPath(item)`), but the release's premise is that the two sites now agree, and this is the case where disagreement matters most.

**Fix:** in hydrate, handle `'proxy'` as `create()` does — substitute `span({ bind: { value: item, binding: 'text' } })`. For shadow-DOM components the existing `warnedShadowContentBindings` check then fires, converting silent dead text into a named warning. Better: extract the whole positional-**to-node** conversion, not just the classification, so the sites cannot express the mapping differently.

### M3 — `restoreCommittedDist()` converts a LOUD "dist deleted" signal into a SILENT "dist reverted to HEAD", past the only ordering-proof publish gate
`bin/site.ts:787` *(verified)*

Sequence, all ordinary: edit `src/` → `bun run build` (fresh uncommitted `dist/`) → `bun start` to eyeball the docs → save any watched file. `rebuild()` runs `buildSite` (prebuild `rm -rf dist`), then `buildDocsBundle()`, then `restoreCommittedDist()`, which `git checkout --`s every tracked `dist/*` back to HEAD — 63 files, including `index.js`/`main.js`/`module.js`/`core.js`/`state.js`/`cli.mjs`. `rebuild()` never calls `buildLibrary()`, so nothing is regenerated. `git status` for `dist/` goes **clean**; a following commit pairs new `src/` with old `dist/`; `bin/check-publish-tag.ts:59-81` asserts existence + trackedness, never freshness, so the gate that fired on the old behaviour (deleted file → `existsSync` false → exit 1) is green.

Three sub-claims in the report are **wrong — do not chase them**: `playwright.config.ts` sets `stdout: 'pipe'` (forwards, not hides) and `DEV_NO_WATCH=1` (honoured), so `rebuild()` never fires in the browser lane; `prepublishOnly` never covered *staleness*, only deletion; and the backstop is mechanical, not a human step — `../tosijs-coding-practices/tools/release-doctor.ts:205-268` rebuilds and git-diffs `dist`/`docs` and FAILs on drift (correctly not a build or publish gate, and in another repo).

Also **not new in kind**: `buildLibrary(!full)` already restored the tjs pair at base, so `./debug` and `./safe` could already be silently stale, and `UPSTREAM.md:243-246` was already inexact. What this diff adds is the restore in the **watch loop** plus widening from 2 files to all 63 — moving the silently-stale surface from two inert experimental subpaths to the package's primary entry points. That widening is the new blast radius.

**Fix:** make staleness machine-visible. Have `restoreCommittedDist()` write a gitignored sentinel (`dist/.restored-from-HEAD`, listing files/timestamp/cwd), announce on **stderr** not stdout, have `buildLibrary(full=true)` delete it after a real rebuild, and have `bin/check-publish-tag.ts` refuse to publish while it exists. Also fix `UPSTREAM.md:243-246`, which now describes a guard that no longer fires.
