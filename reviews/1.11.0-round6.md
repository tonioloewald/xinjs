## Blockers (fix before tag)

### B-1 — `describe()` publishes a password in cleartext inside the record it stamps `secret: true`
`src/agent.ts:2346` · security · **verified** · *severity as filed*

`recordFor`'s binding loop computes `boundValue(b.path, twoWay, record.secret === true)` at :2342-2347, ~70 lines before `suppressHarvest` sets `record.secret = true` from the containment arm at :2418. At that moment `record.secret` is only `describeElement`'s element-or-ancestor answer, which is **false for a container**. Reproduced at HEAD under posture `expose: { roots }`:

- `div({ bindValue: r1.pw })` wrapping `<label>Password <input type="password"></label>` → `{"tag":"div","value":"CLEARTEXT-R1 ⟷ r1.pw","secret":true}`
- light-DOM component, value binding on the host, password one `<div class="row">` deeper → same shape
- `data-tosi-secret` custom element one div inside a bound `<form>` → same shape

The shadow twins are correctly redacted, so this is a light-DOM-only channel. The record self-contradicts: static text withheld under containment, bound value published in the same object. `read()` on those paths also returns cleartext, so the root gap is secret-path *learning*, not record ordering.

**Fix:** ask the containment question once before the binding loop — `const contentSecret = harvestWouldLeak(el, record, allBoundPaths)` (pure, does not mark) — and pass `record.secret === true || contentSecret` as `boundValue`'s third argument. **Do not assign it to `record.secret`**: line 2340's `if (record.secret === true) addSecretPath(b.path)` is the round-4 path-poisoning route and must keep seeing element-or-ancestor secrecy only. The durable fix for the `read()`-before-`describe()` half belongs in `refreshSecretPaths`, with the same `propagates` narrowing. Pin with the three fixtures asserting the token substring is absent from `JSON.stringify(describe())`, keeping the round-4 control (`read('c41a.theme') === 'dark'`) beside them.

### B-2 — `propagates` never reads `autocomplete`, so a hidden `cc-number` / `one-time-code` field leaks in cleartext — contradicting the shipped CHANGELOG
`src/agent.ts:1365` · correctness + security · **verified** · *escalated from major: one-line fix, shipped prose asserts the opposite*

`const propagates = el.hasAttribute?.('data-tosi-secret') === true || kind !== 'hidden'` keys only on `type`. Executed: `form({ bindValue: cc.pan })` containing `input({type:'hidden', autocomplete:'cc-number'})` → `read('cc.pan')` returns `"4111111111111111"`; the `type:'text'` twin returns `⟨secret⟩`. `one-time-code` behaves the same. The cleartext reaches **both** `read()` and the serialised `describe()`. The same element returns `⟨secret⟩` through the shadow arm, so light and shadow disagree on identical markup.

`src/agent.ts:1355` and `CHANGELOG.md:143-144` both state "propagate only for a password, a `cc-*`-style autocomplete, or an explicit `data-tosi-secret` — never a **bare** `input[type="hidden"]`". The word doing the work is *bare*, and the code has no notion of it.

**Fix:** `|| hasSecretAutocomplete(el)` (the prefix helper already exists above `SECRET_CONTROL_SELECTOR`). Pin with a hidden `autocomplete="cc-number"` fixture next to the existing bare-hidden control that must stay readable — `src/agent.test.ts:3312` has fixtures for bare-hidden, `data-tosi-secret`-hidden, text and password, but none for the overlap, which is why the suite is green.

### B-3 — the only prose in the npm tarball declares `#41` closed over at least six reproducible cleartext shapes
`CHANGELOG.md:119-153` · security + docs · **verified** · *escalated from major: shipped prose, and the issue is being closed*

`CHANGELOG.md` is the sole prose in `package.json` `files` (`docs/` and `llms.txt` are not). It claims coverage of "the owning `<form>`, **at any depth**", names `data-tosi-secret` as a strong-evidence propagator, and calls marking the control or region "the recommended belt-and-braces mitigation". `TODO.md:8` marks `#41` `[x] BOTH cases fixed`; the commit is titled "close tosijs#41 completely". Shapes verified to return cleartext at HEAD:

1. `div({bindValue}) > label > input[type=password]` — wrapping a control in its own `<label>` defeats the one-step parent arm outright.
2. Light-DOM component, binding on host, password in a row `<div>` — the shadow twin redacts, so **light-DOM components are now strictly weaker than shadow ones**, and light DOM is a first-class Component mode.
3. `<form bindValue> > div > <my-field data-tosi-secret>` — `el.form` is `undefined` on a custom element **including a `formAssociated` one** (the spec puts the owner on `internals.form`), so the explicit author marker is **weaker than the heuristic**.
4. `<form bindValue> > div > <div data-tosi-secret> > input` — same cause; a region marker never reaches its owning form.
5. `<form bindValue> > div > <shadow component containing input[type=password]>` — `el.form` is null across a shadow boundary, and the shadow arm only inspects the immediate host.
6. `div({bindValue}) > div > div > input[type=password]` — two light levels, still cleartext.

Worse, the one in-source caveat is **stale**: `src/agent.ts:1336` warns that `<form bindValue> <div> <input type=password>` "is still not learned, and tosijs#41 stays open for it" — that exact fixture now returns `⟨secret⟩`. So the code documents a case that is fixed and nothing documents the six that are not.

**Fix (minimum, prose-only, Tier 0 re-review):** correct the section to state the residual explicitly — "one light level up, plus the owning `<form>` for native controls within the same tree" — name the uncovered shapes, point at `data-tosi-secret` **on the control** as the mitigation, add the affected-version sentence, reopen `#41` and un-tick `TODO.md:8`. **Cheap code extensions worth taking with it** (each is declared DOM ownership, not a distance guess): harvest through `el.labels`; climb to the nearest **custom-element** ancestor as the light twin of the `.host` arm (a `<div>` app shell is not a custom element, so the round-4 hazard does not apply); read `(el as any).form ?? (el as any).internals?.form`. If the arms widen, re-review scope is security + correctness over `refreshSecretPaths` plus **all four existing over-redaction controls**.

### B-4 — round-5 B-1's remediation does not take: `delete record.checked` sits behind `record.text === undefined &&`
`src/agent.ts:2417` · security · **verified** · *escalated from major: it is the remediation of a prior blocker, and it leaks*

`input({ type:'checkbox', bindValue: p2.twoFactor, bindText: p2.caption })` beside a `data-tosi-secret` checkbox on the same path: `read('p2.twoFactor')` → `⟨secret⟩`, while `describe().wiring[1]` is `{"tag":"input","label":"mirror","type":"checkbox","checked":true,…}` — published, and the record does not even carry `secret: true`, because a defined `record.text` short-circuits the `&&` before `suppressHarvest` is called. The other two call sites carry the same shape (contenteditable behind `record.value === undefined` at :2479; structural tier behind `heading &&` at :2676) — those two cost only the `secret: true` marker, since `boundValue` redacts independently.

`src/agent.ts:1592-1594` and `CHANGELOG.md:108-111` both claim "a live-state field added later inherits the guard instead of needing another gate". It inherits it only when the author's markup happens to carry no text binding — a property of the markup, not the code. This is the ninth address of the invariant round 5 asked to be closed structurally.

**Fix:** call `suppressHarvest(el, record, allBoundPaths)` **unconditionally, exactly once**, immediately after the data-binding loop, and use its boolean result in the three harvest conditions — so "does this record already have text" becomes a separate question from "may this record carry content". Add the `bindText`+`bindValue` checkbox fixture; the shipped B-1 test uses a bare mirror and passes either way.

## Majors (not blocking the tag, but decide them before it)

### M-1 — the shadow arm still propagates from a bare `input[type="hidden"]`, and its negative control is inert
`src/agent.ts:1301` · correctness + blast-radius · **verified** *(two lens findings deduped)*

A component whose host carries a `fromDOM` binding and whose **shadow** tree contains `<input type="hidden" name="csrf">` — no secret involved — makes `read('sh.token')` return `⟨secret⟩` **permanently for the process**: `secretPaths` is module-level and append-only, and survives `agent.disable()`, removal of the host, and re-enabling. The byte-identical light-DOM shape is now correctly readable and pinned (`c41c`, `src/agent.test.ts:3455`). Shadow DOM is tosijs's **default** for Components, so this is the more likely half. Fail-closed (availability, not disclosure) — hence major, not blocker.

The existing regression test at `src/agent.test.ts:2954` ("a hidden input in a component does not redact the host binding") binds with `bindings.text` (toDOM-only), so it is filtered by the *other* narrowing and never exercises hidden-input propagation at all. Swapping it to `bindings.value` fails. That is worse than no control: it reads as coverage and provides none.

The diff calls the asymmetry deliberate at `src/agent.ts:1358-1360`, and `TODO.md` files it as "should be a decision, not a leftover". **Before tag, make it a recorded keep-decision naming the shipped hazard, or hoist `propagates` above the shadow arm** — and either way add the shadow mirror of the `c41c` control and fix the inert test. Also note the shadow arm keys on `getRootNode()`, so the hidden input need not be a direct child.

### M-2 — a real happy-dom node-identity defect was absorbed as a private code comment
`src/agent.ts:1393` · blast-radius · **verified** · *remedy is upstream + CLAUDE.md, see follow-ups*

happy-dom 20.11.1 returns a `Proxy` from `HTMLFormElement`'s constructor (`lib/nodes/html-form-element/HTMLFormElement.js:38`; `HTMLSelectElement.js:42` too), while internal parent/child links hold the raw target. So `input.parentElement === form` and `input.closest('form') === form` are **false**, while `input.form`, `querySelector('form')` and `document.forms[0]` are true. Measured consequence in this repo: `elements.form({ onClick })` containing a button fires the handler **0 times** on a bubbling click; the `elements.div` twin fires once — because all binding/handler metadata is WeakMap-keyed (`src/metadata.ts:314,384`) and delegation walks upward (`src/bind.ts:545,770`).

Nothing ships broken today (the three new `<form>` tests route through `el.form` and genuinely pass). The cost is that the next test touching `<form>` — the primary container for `fromDOM` bindings, i.e. the surface this release hardens — goes green while testing nothing, which is the exact environment-suppressed-assertion class CLAUDE.md already institutionalised for `getBoundingClientRect`. Two corrections to the finding, both understating it: `isSameNode` is **false** (so it does not mask the break), and it is **not form-specific** — `<select>` breaks identically; `div`/`section`/`fieldset`/`table`/`label` chains are clean.
